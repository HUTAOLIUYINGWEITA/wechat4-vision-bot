# 踩坑记录（WeChat 4.x 像素/OCR 自动化）

> 这里记录的是本项目在**真机**上真实踩过的坑。很多坑是"看代码/看自测完全正常，一上真机就全灭"，
> 所以这份文档可能比源码更有价值。**改代码之前先看这里，尤其是标了「别再改回去」的条目。**
>
> 说明：为保护隐私，文中真实群名/昵称一律用「某个长中文群名」「某个群聊」等占位描述代替。

---

## 1. 搜索下拉第 1 项是「搜索网络结果」，回车会打开「搜一搜」网页

**现象**：`Ctrl+F` 输入会话名后，按 `Enter` 以为会进入会话，结果弹出一个「搜一搜」网页窗口，
聊天窗口没有任何变化。

**原因**：微信 4.x 的搜索下拉里，第 1 行是 `💥 搜索网络结果`（本质是命令条目），默认高亮；
`Enter` 触发的是它，不是聊天会话。而且会拉起新进程 `WeChatAppEx.exe` 抢前台，把微信挤到后面。

**修法**：
- **绝不回退成"输入名字 + Enter"**。整条链路改成：
  整窗截图 → OCR 下拉 → 按图标/分组判定「真正的会话行」→ 受控单击 → 标题校验 → 再输入正文。
- 显式排除命令条目关键词：`搜索网络结果 / 搜一搜 / 打开 / 恢复数据 / 已读 / 粘贴 …`。
- 日志里凡出现「按 Enter 打开会话」就是回归，直接当 bug。

**别再改回去**：永远不要用 Enter 打开会话。

## 2. 真会话在「功能」分组下，回车打不开，只有点击才行

**现象**：搜索「文件传输助手」，下拉里能看到 `功能` 分组下的目标行，但纯键盘 `↓ + Enter` 毫无反应；
某些情况下 `↓` 还会跳到别的分组。

**原因**：微信 4.x 的下拉是「分组 + 行」的两级结构，键盘焦点行为在 Qt 自绘 popup 里不可靠；
真会话行只响应鼠标点击。

**修法**：
- 用 OCR 行坐标 + 图标颜色判定行类型（彩色头像 = 会话行；灰色放大镜 = 聊天记录/命令条目）；
- 计算行中心点，把坐标夹在**微信窗口矩形内**再单击；
- 单击后立刻 OCR 校验聊天标题 == 目标会话名，不符就 abort。

**别再改回去**：不要试图用键盘导航下拉列表。

## 3. 中止后盲按 `Esc` 会把微信窗口「收进托盘」（用户以为被关了）

**现象**：某次异常中止时脚本"顺手"按了 `Esc`，用户发现微信窗口消失了，以为程序把微信关了。
实际是微信 4.x 把主窗口**隐藏到了托盘**（`IsWindowVisible=False`），进程还活着。

**原因**：`Esc` 的作用域取决于当前焦点：搜索层没打开时，`Esc` 落在微信主窗口上 → 微信 4.x 的
「按 Esc 关闭到托盘」行为被触发。

**修法**（`reply.py` 的 Esc 规矩）：
- 只有**已确证搜索层打开**（`Ctrl+F` 后像素差确证 + 前台是微信）时才允许按 `Esc`；
- 确证记录超过 8 秒视为过期，过期后**一个 Esc 都不发**；
- 任何 `Esc`/点击之后都做**窗口存活校验**（`IsWindow` + `IsWindowVisible` + 尺寸合理），
  窗口丢了 → `[ALERT] wechat-window-lost` → abort，不连点、不继续注入；
- 释放按键走 `finally`，任何异常路径都不会把键按住不放。

**别再改回去**：「无脑 Esc 清理状态」是曾经把用户微信弄丢的根因。

## 4. 小字号 OCR 会丢字 → 放大 2~2.5 倍 + 多 PSM 合并才稳

**现象**：下拉面板里 13 字的长中文群名，tesseract 直接读会丢字/插竖线
（例如读成 `听|遂名长...` 这种），`exact` 匹配永远失败 → 每次 abort → 会话永远打不开。

**原因**：微信 4.x 下拉行的字号很小（125% 缩放下约 13~14px），tesseract 在原始分辨率下对
小字号中文的分割质量很差；不同 PSM 模式还会**各自丢不同的字**。

**修法**：
- 先把区域**放大 2.0 倍**（`INTER_CUBIC`）再 OCR；
- 同一张放大图跑 **PSM 6（段落）+ PSM 11（稀疏文字）两遍**，行级取并集；
- 再跑一遍**原始未放大**做对照（日志打 `[OCR对照] 放大版/原始版`，失败截图能直接定位问题）；
- 第一遍选不中时，只裁「下拉面板区域」放大 2.0x 重扫，再对候选头像行做 **PSM 7 单行精读**；
- 匹配加「近似唯一」档：覆盖率 ≥ 0.60、精确率 ≥ 0.75、领先第二名 ≥ 0.15 才先点，
  **安全闸仍在点开后的标题校验**。

**别再改回去**：不要退回"纯 exact 匹配"（真机必炸）。

## 5. 长文本 `SendInput` 逐字注入会丢字/重字（`：：`、`『『` 现象）→ 必须剪贴板 + 三重校验

**现象**：一段较长的告警文本发出去变成类似
`小耳朵提醒：：不到会话『『XXX』』』检查白名单名字或微信是否改名（（因=row--pproximate）`
—— 全角标点成对重复、丢字、还混进了内部原因串。

**原因**：`SendInput` 逐字符注入在长文本时会丢/重（输入法/焦点/时序问题），而旧的"覆盖率"校验
（单看字符集合）竟然放过了这条乱码。

**修法**：
- **规则**：`len(text) > 12` 或含全角标点/引号/括号 → **一律走剪贴板 `Ctrl+V`**；短文本才用 `SendInput`；
  两条路互相兜底重试一次，仍不过 → `type-verify-failed` abort，**绝不按 Enter**。
- **三重校验**（`input_text_metrics`，日志打 `chars=xx/xx(ratio) cover=.. seq=.. dup=..`）：
  1. 字符数比例 ∈ `[0.85, 1.25]`；
  2. 去重字符集覆盖率 ≥ 0.90；
  3. `SequenceMatcher` 相似度 ≥ 0.75；
  4. **另加「相邻重复标点」检查**（期望文本里没有 `：：`/`『『`/`((`/`--` 时，实际 OCR 出现即判失败）。
- 实测：旧路径靠覆盖率能蒙混过关，是「重复标点检查」把它拦下来的。

**别再改回去**：不要只保留 `SendInput`，也不要只保留"覆盖率"单判据。

## 6. 离线自测用大窗口截图能过，小窗口真机过不了（字号变了）

**现象**：用历史大窗口截图跑离线回归全 PASS，真机（窗口较小/字号不同）却一直 abort。

**原因**：
- 微信窗口大小不同 → 会话行字号/行高/间距都变，写死的像素阈值（行距、热区、图标区域）全偏；
- 自测截图是「某一时刻、某个窗口尺寸、某套字体」的快照，不能代表所有真机状态。

**修法**：
- 所有几何量都从**当前截图里动态算**（OCR 行距中位数、面板边界、输入框区域），不写死像素；
- DPI 用 `GetDpiForWindow` 实时换算（见第 8 条）；
- 自测区分「构造用例（纯逻辑）」和「真实语料用例（可选）」——没有语料时**跳过**而不是 FAIL；
- 真机验收必须用**目标机器 + 目标窗口大小 + 目标字号**跑一遍。

**别再改回去**：出现"自测全过、真发全灭"时，先怀疑自测和真机的窗口/字号不一致。

## 7. 微信 4.x 的 Qt 下拉是 popup，`PrintWindow` 抓不到 → 必须整屏截图

**现象**：用 `PrintWindow` 抓微信主窗口，截图里**没有搜索下拉面板**（下拉是独立 popup 窗口）；
OCR 找不到任何会话行。

**原因**：Qt 的下拉弹层是独立的 topmost popup，不在主窗口的绘制树里；`PrintWindow` 只画主窗口。

**修法**：
- 检测层用 `PrintWindow`（不抢焦点、可后台抓图，适合"盯未读"）；
- **定位下拉时必须整屏截图**（`ImageGrab`），并在截图前校验前台窗口属于微信进程，
  否则 abort（防止在游戏/浏览器画面上定位点击）；
- 截屏/点击坐标统一用 DPI 比例换算到物理像素。

**别再改回去**：不要指望 `PrintWindow` 能抓到下拉面板。

## 8. DPI 125% 下行距/热区全部要按比例换算，别写死像素

**现象**：在 125% 缩放下，旧代码写死的行距阈值 `gap > 62` 实际只剩 ~6.7px 余量，稍微变字号就选错行。

**原因**：Win32 逻辑像素 ≠ 物理像素；不同缩放比例下同一布局的像素值全部不同。

**修法**：
- 进程启动时 `SetProcessDpiAwareness(2)`（per-monitor v2）；
- 所有坐标从 `GetDpiForWindow(hwnd) / 96.0` 得到 `scale`，按比例换算；
- 行距阈值改成「OCR 行距中位数动态计算」而不是常数；
- 点击坐标夹在窗口矩形内（物理像素），越界 abort。

**别再改回去**：不要在代码里出现写死的像素阈值。

## 9. 判断「是不是在打游戏」只能按进程名，不能拿窗口标题匹配

**现象**：用户在 Edge 里看「坦克世界」的视频，项目却判定"正在打游戏" → 一条消息都不回：
`skip: busy (reason=foreground-game) 前台进程='msedge.exe'（title='【坦克世界】…'）命中游戏名单 '坦克世界'`。

**原因**：旧 `busyguard._match_game()` 把 `exe` / `exe_base` / **`title`** 三个字段一起拿去撞游戏名单，
而名单里有一个裸中文词「坦克世界」→ 浏览器标题命中。

**修法**：
- 判定**只按进程名**：带 `.exe` 的名单项与 exe 文件名精确匹配，不带 `.exe` 的按进程名前缀匹配；
  **窗口标题永远不参与**；
- 从游戏名单里删掉裸中文词，只保留可执行文件名（`WorldOfTanks.exe`、`cs2.exe` 等）；
- 日志写明 `匹配字段=进程名(精确/前缀)、匹配值=…，窗口标题不参与判定`。

**别再改回去**：标题匹配会让「看游戏视频」「看直播」全部误杀。

## 10. 曾误判「微信以管理员运行导致 UIPI 屏蔽」，实测 `TokenElevation=0`

**现象**：某次真机上 `Ctrl+F` / 点击 / `SendInput` 全都"没有界面变化"（多次截图逐像素相同），
当时的判断是：微信被以管理员权限启动（High 完整性），我们的 Agent 是 Medium，
Windows 的 **UIPI（用户界面特权隔离）** 把模拟键鼠全拦了。为此一度把项目停了、要求用户改用普通权限重启微信。

**后来的实测**：查进程 token 的 `TokenElevation` → **0**（并未提权）。
也就是说「微信以管理员运行」这个假设**不成立**，UIPI 不是那次问题的原因。

**教训**：
- 不要用 `whoami /groups` 的某一项或"看起来没反应"直接推断 UIPI；要看进程 token 的
  `TokenElevation` / 完整性级别实测值（两边都查）。
- 排查顺序应该是：窗口是否可见/可用 → 前台是谁 → 目标控件位置是否对（先截图看一眼）→
  再怀疑权限。真机问题九成在"窗口状态/焦点/坐标"，不在权限。

**别再改回去**：把「UIPI 屏蔽」当成默认解释会导致误停项目、误让用户改环境。

## 附：其它值得记住的坑（同样别再犯）

### A. 两个 watcher 进程 = 同一条消息回两遍

重启前必须先杀旧进程（`toggle.ps1 off/stop/panic` 都做了），否则两个水印/两套状态文件互相踩，
同一条未读会被回两次。`watcher.lock` 里的 pid 不可尽信（可能是僵尸/被 pid 复用），
杀之前要校验该 pid 的命令行含 `watcher.py`。

### B. `toggle.ps1 on` 只改配置不起进程 = "看起来打开了其实没干活"

旧版 `on` 只写 `enabled=true`，不设 `autoSend`、不启动 watcher 进程 → 面板显示已打开，实际一条不回。
现在的语义：`on` = 起进程 + autoSend + 删 STOP；`off` = 杀进程 + 关开关；`stop` = 只杀进程；
`panic` = 立即急停。判断是否真在岗要看 `toggle.ps1 status` 的**进程行/结论行**，不要只看 `enabled`。

### C. `.ps1` 要 UTF-8 带 BOM，`.cmd` 必须 CRLF 且纯 ASCII，而 JSON 绝对不能有 BOM

- `toggle.ps1` / `toggle-ui.ps1` 走 Windows PowerShell 5.1，中文 .ps1 若没有 BOM 会显示成乱码；
- `.cmd` 用 LF 换行会被 cmd 解析错（`'rshell' is not recognized` 之类）；
- 反过来 **JSON 配置（含 `config.json`）绝不能有 BOM**：PowerShell 5.1 的 `Set-Content -Encoding UTF8`
  默认带 BOM，写进 `config.json` 后 `json.load` 直接报 `Unexpected token '\uFEFF'`。
  写 JSON 请用无 BOM 写入并回读校验。

### D. 搜索框 OCR 不能当硬闸门

长会话名在搜索框里的 OCR 召回率可能只有 0.5 左右，拿它当"必须通过"的闸门会永远 abort。
正路判据是「下拉面板里定位到了会话行」，搜索框 OCR 只作辅助告警。

### E. 空输入框的 placeholder 会造成 OCR 幻觉

微信空输入框的 placeholder「长按鼠标 语音输入」被 OCR 读成「-一 让 一 * 长按和鼠标 语音输入」这类噪声，
旧判据「≥2 个连续汉字 = 输入框有残留文字」会误 abort。要先去掉 placeholder 短语，
再只认「目标名字符覆盖 ≥50% 或目标名前 2 字出现」，无目标名时才退化为「≥3 连续汉字」。

### F. 单元级 OCR 幻觉会造成误 abort

输入框区域是深色空白，tesseract 会对空白/小图标 hallucinate 单字（实测出现过 `站` / `屈` / `一`）。
「任意非空文字 = 输入失败」的判据会让三重校验永远不过 → 改为**只有 ≥2 个字符的 OCR 结果才算证据**。

### G. 发送完主动还原前台会把微信甩到后台

用户原话："输出一个虚拟的 Enter 就欧克了，但她把微信切到后台了"。
现在默认**保持微信在前台**（`reply.restoreForeground=false`），只有显式设 `true` 才恢复旧行为。

### H. 自测全过、真发全灭的两个真 bug（值得记住的教训）

1. `find_conversation_row` 走了「行级 OCR（`_ocr_tsv_lines`）」而不是「词级聚类（`_ocr_rows`）」，
   会把下拉行和右侧聊天区同一 y 的文字拼成一行（`| 文件 传输 助手 | 文人 助手`）→ exact 永远失败；
   而离线自测走的是词级路径，**发现不了**。
2. `_try_dropdown` 成功路径返回 5 元组、调用处按 4 元组解包 → `ValueError: too many values to unpack`，
   表现是"会话行点开、标题校验都过了，然后必崩"。

教训：**离线自测要尽量走和真机相同的路径**；返回值/元组结构这种低级错误，用 `py_compile` 是查不出来的。

### I. 双击 `.cmd` 结尾的 `pause` 会卡住自动化调用

调试时方便，但被脚本/CI 调用时会卡死。自动化调用时用 `Start-Process -RedirectStandardInput <空文件>` 喂 EOF。

---

**最后一条**：这个项目里所有"安全 abort"都不是 bug——宁可漏回一条消息，也不要回错人、发半截话、
把微信窗口弄丢。看到 abort 先看日志里的 `reason=`，再对照本文档找原因。

## 11. 触发词用「严格字符串匹配」= OCR 错一个字，整条远程指令静默失效

**现象**：用户在群里发
`小耳朵，给你个任务，把桌面 X 发到某群，一级密码 ******`，
机器人没有转告给 Agent，而是当成普通闲聊回了一句「这个我弄不了，你直接找 Agent 吧」。

**原因**：触发判定是 `if "小耳朵" in raw`。聊天区 OCR 把**「小耳朵」读成了「小耳洲」**
（朵 → 洲，只错一个字），字符串不匹配 → 判定「这不是给我的指令」→ 走闲聊分支。
更糟的是长消息里的密码也常被读错（`一级密码: 061110` → `一级 空色: ******`），
就算触发词蒙对了，密码校验也会挂。

**修法**：
- 触发词改**模糊识别**，满足任一即算命中：
  1. 含 `小耳朵`（原逻辑）
  2. 正则 `小耳[\u4e00-\u9fa5]`（「小耳」+任意汉字，覆盖 小耳洲/小耳朱/小耳采…）
  3. 与触发词字符覆盖率 ≥ 0.67
- **含触发词但密码读不出来 → 走「问密码」挑战-应答**（回「要做这个得先核对密码」），
  **绝不当成闲聊**；这种情况算 `need_password`、**不计入密码错误次数**。
  用户只需再单独发一条纯数字（短消息 OCR 准确率高得多）。

**别再改回去**：触发词判定不要只有 exact 字符串比较；代价是有人喊「小耳X」会触发流程，
但**执行门槛仍是密码**，所以安全边界没变。

**权衡**：触发词仍必须出现（不出现就一律闲聊），这样群里别人聊天时才不会误触。

## 12. 白名单靠 OCR 认群名 → 同一个群「时灵时不灵」

**现象**：同一个群，有时候正常回复，有时候完全没反应；日志里是
`whitelist miss: display='BBB示例测械群'`，而白名单配的是 `BBB示例测试群`。
下一次 OCR 读准了就命中，读歪了就 miss，**而且 miss 还会写「已处理」指纹 → 这条消息永久不回**。

**原因**：旧判定是 prefix/包含式匹配，对 OCR 噪声极敏感。用户体感就是「她有时理我有时不理」。

**修法**：
- 改成**闭集判别**：白名单只有几个已知名字，判断「是哪一个」远比自由匹配容易。
  每个 OCR 候选 × 每个白名单项算三分（difflib 55% + 字符集重叠 30% + 长度相似 15%），
  最高分 ≥ 0.55 且领先第二名 ≥ 0.12 才命中。
- **多候选全部参与、取最高**：OCR 常常给出 3 个候选，其中往往有一个更接近
  （实测 `BBB示例测群` 能到 0.83，而只取第一个候选就是 0%）。
- **miss 时不要写 `processed_fingerprint`**，只做 45 秒短冷却，允许下一轮重新判断。

## 13. 长消息折行后会被当成「多条消息」，最后只剩一个字的碎片

**现象**：用户发了一条折成 4 行的任务消息，机器人收到的却是
`['人和', '件']` 这种碎片，于是只能回一句「嗯嗯，在的」。
而中间层日志里其实**已经 OCR 出了接近完整的句子**，只是被择优逻辑丢掉了。

**原因**：气泡聚类按固定垂直间距切分，一条长消息折行成多行就被切成了多个「气泡」；
随后「整块 vs 精读」的择优规则取了字符数最少的那个。

**修法**：
- 聚类改成**自适应气泡内行距**：先从同方向 + 左缘 ±10px 对齐的相邻行 gap 里取较小一半的中位数
  作为 `intra`，`split_gap = intra * 1.6`，只有明显大于气泡内行距才切新气泡。
- 气泡内多行**按 y 顺序拼接**，并剔除「被更长候选完整包含 / 90% 相似但短很多」的碎片。
- **硬规则：最终采用的文本不得低于最长候选的 50%**，否则退回最长候选。
  这一条直接杜绝了「有 60 个字却采用 1 个字」。

## 14. 短文本 + 中文标点 → 校验必挂（「嗯嗯，在的」永远发不出去）

**现象**：输入框里明明有字，OCR 也读到了 5 个字符，但校验判定失败：
`chars=5/5(1.00 OK) cover=0.75(BAD) seq=0.60(BAD)` → abort，不按 Enter。
屏幕上看起来像「同一句话被写了又擦、擦了又写」，用户以为程序在抽风。

**原因**：
1. OCR 把中文逗号 `，` 丢了 → 覆盖率从 1.0 掉到 0.75；5 个字里错 1 个就是 20% 误差；
2. 阈值是**固定值**（cover ≥ 0.85 / seq ≥ 0.80），对短句太苛刻；
3. 像素差兜底当时只在 `OCR 读到 0 个字符` 时才启用，而这里 OCR 读到了字，兜底没被走到。

**修法**：
- **比较前先剥标点**（中英文标点全去掉），只比汉字/字母/数字；
- 阈值**按去标点后字数分三档**（L1 ≤6 字：0.60/0.50；L2 7–15：0.80/0.70；L3 >15：0.85/0.80）；
- 像素差兜底条件改成「**只要 OCR 判不过** 且 pixdiff ≥ 0.002」，日志打 `evidence=ocr|pixdiff|none`。
- 重试次数 2 → 1（每轮重试都会清空重打，用户看着像"写了又擦"）。

## 15. 去重闸误杀正确答案：消息是新的，凭什么不能回？

**现象**：机器人**已经生成了完全正确的回复**「在的，火锅吧」，却被拦掉：
`skip: duplicate-text（同一句话 600 秒前已发过）` → 用户等了 3 分钟什么都没收到。

**原因**：同句去重的窗口 600 秒太长，且命中后直接丢弃，还写了「已处理」指纹。

**修法**：
- 窗口改 `dedupeSameTextWindowSeconds`（默认 **60 秒**）——这条闸的本意是防代码循环复读，
  不是长时间禁言；
- **命中后不丢弃**：把「最近已说过的话」塞进提示词，让模型**换一种说法重新生成**
  （`duplicateRegenAttempts`，默认 2 次）；仍撞车就记日志 + 走提醒通道，绝不静默丢弃。

## 16. 被限流跳过时写 `processed_fingerprint` = 这条消息永远不回

**现象**：用户连发 5 条，机器人只回了 2 条，另外 3 条「没反应」。
日志：`skip: per-chat-interval（距上一条只过了 27s）-> 写 processed_fingerprint 防反复生成`。

**原因**：限流跳过被当成「已处理」，指纹一写，这条未读就再也不会被处理。

**修法**：限流命中一律**入队**（`pendingQueue`）：
- 记 `{chat, texts[], fingerprint, expireAt}`，**不写 `processed_fingerprint`**；
- 冷却结束后把该会话的多条消息**合并成一条回复**，只生成一次、只发一次；
- 队列有 TTL（默认 600s）、失败退避（20s × 3 次），过期丢弃也写日志。

## 17. 模型**根本看不到图** —— OCR 才是它的眼睛

**现象**：机器人总是回「嗯嗯，在的」「没看懂，你再说一遍？」这种敷衍话，怎么调人设都没用。

**原因**：排查后发现 `genreply.py` **没有任何多模态支持**（`image_url` 命中 0 处）。
整条链路是：截图 → Tesseract OCR → **文字** → 模型。模型从头到尾没见过画面，
它拿到的永远是 OCR 认歪的字（「今晚吃什么」→「天钠还十距闭」）。
所以"识图差"其实是 **OCR 差**，跟模型能力无关。

**修法**：视觉优先（详见 README 的「视觉理解」一节）——
只读打开会话 → 裁出聊天区底部 PNG → base64 以 `image_url` 送多模态模型 →
OCR 只作参考并在提示词里标注「可能不准，以图为准」；视觉失败自动降级为纯文本。

**实测**：`deepseek-flash` 与 `deepseek-v4-pro` 都接受 `image_url`；
注意**过小的图（如 8×8）会被拒**（`unsupported image`），裁剪图短边保持 ≥ 64 即可。
带图请求约 840–880 prompt tokens（纯文本约 500–530）。

## 18. `memo_log` 的可用性检查返回类型不一致 → 记录功能从未成功过

**现象**：审计里每条备忘录记录都是 `ok: false`，
`err = "wechat-unavailable: check-error: cannot unpack non-iterable bool object"`，
但微信明明开着、窗口也正常。

**原因**：可用性检查函数有一处返回**单个 bool**，调用方却按 `(ok, why)` 元组解包。

**修法**：统一约定 `_memo_wechat_available() -> (ok: bool, why: str)`，
所有调用点按元组解包（兼容历史 bool 返回），`why` 为空串表示可用。

**教训**：凡是"检查 → 解包"的辅助函数，返回值形状必须写进函数名或注释里；
这类 bug 在日志里只表现为一句 `check-error`，很容易被当成"微信不可用"忽略过去。

## 19. `Ctrl+F` 会被聊天输入框"吃掉"，导致 `search-layer-not-opened`

**现象**：`reply.py` 连续两次 abort：
`search-layer-not-opened（Ctrl+F 后输入的目标名跑进了聊天输入框）`。
好消息是守卫生效了：`已清理残留=True；未点击任何行、未输入正文、未按 Enter`，**没有误发**。

**原因**：在刚刚手动操作过微信（点过会话、发过文件）之后，焦点停在聊天输入框里，
`Ctrl+F` 没有被搜索层消费，后续输入直接落进了输入框。

**修法（待完善）**：调用前先把焦点从输入框移开（例如点一下会话标题栏/消息区空白处），
或在 Ctrl+F 之后**先确认搜索层出现**（这一步目前已经是硬闸门，所以最坏情况是 abort 而不是误发）。

## 20. 搜索下拉对某些群只出「聊天记录」，没有「群聊」行 → `sendfile.py` 找不到会话

**现象**：`sendfile.py --chat 某个群 --file X` 两次都 abort：
`没有搜到会话 某个群，最像的只有 0% 字符覆盖`，`stage=abort row-approximate`。
但搜索框里**输入是成功的**（OCR 命中目标名，覆盖率 100%），左侧会话列表里那个群也明明在。

**原因**：该群的搜索结果里只出现了「聊天记录」分组（命中了消息正文），
没有出现「群聊/联系人」分组，于是下拉里不存在可点击的会话行。

**临时绕过**：手动点左侧会话行 → 点输入框的「文件」按钮 → 文件选择框里填绝对路径 → 发送。

**待完善**：给 `reply.py` / `sendfile.py` 增加「列表直点」模式——
当搜索下拉里没有会话行、而左侧会话列表里能 OCR 到目标名时，直接点列表行打开会话。

## 附：一句总结

真机上最难的从来不是「怎么点」，而是 **"我以为它读到了，其实它读到的是另一串字"**。
所有坑里，超过一半都是 OCR 幻觉/丢字导致的**静默错误**——
所以这套系统的核心设计原则是：**任何一步读不准，就 abort，绝不猜**。
